# Historical BM25 + GPT-OSS answer evaluation

This page explains the saved **20-question answer baseline** and how its older scripts work. It is not the setup guide for the current hybrid/Claude application. For current evaluation tools and pending work, read [Evaluation](EVALUATION.md) and [Current status](STATUS.md).

The experiment reused saved BM25 search results, generated answers with `gpt-oss:20b-cloud`, then used the same model to grade them. Ollama exposes that cloud model through a local API; this does **not** mean inference stays on your computer.

## Start by reading the saved results

You do not need a model call to inspect the existing experiment.

| File in [outputs/alex_evaluation](../outputs/alex_evaluation/) | What it contains |
| --- | --- |
| `questions_20.json` | The curated questions and dataset reference answers |
| `bm25_cases_20.json` | The question/evidence batch built from saved BM25 predictions |
| `bm25_gptoss_answers_20.json` | Generated answers, selected evidence, citations and usage |
| `bm25_gptoss_evaluation_20.json` | Model-judge scores and explanations |
| `rag_evaluation_results.xlsx` | The historical human/judge comparison workbook |

The question selection has exactly 20 unique question IDs. It is an input, not a random sample generated by these scripts. Search predictions came from [the saved development run](../evaluation/results/bm25_full_development/predictions.jsonl), introduced in commit `5cd05ea`.

| Dimension | Mean model score, 0–2 | Cases scored 2 |
| --- | ---: | ---: |
| Correctness | 1.30 | 11/20 |
| Completeness | 1.20 | 9/20 |
| Citation support | 1.55 | 15/20 |
| Abstention/limits | 1.70 | 16/20 |

Fifteen answers were given and five marked insufficient evidence. These are historical model-judge results, not validated scores for the current app. The same model generated and judged the answers, and committed code does not fully reproduce the human-agreement report.

<a id="1-prerequisites"></a>
## Before attempting a rerun

Use Python 3.11 and the declared [requirements](../requirements.txt). The examples below use `python` from an activated environment, from the repository root. On Windows PowerShell you can use `.\.venv\Scripts\python.exe` instead; on macOS/Linux, use `.venv/bin/python`.

```sh
python -m pip install -r requirements.txt
python -m pytest tests/test_answer_metrics.py -q
```

A real rerun also needs the raw EnterpriseRAG-Bench checkout and its `generated_data/uuid_index.json`, the approved 20-question selection, saved predictions, and an available Ollama service at `http://localhost:11434`. Follow [dataset setup](WEB_APP.md) rather than guessing paths. The raw corpus and model access are not supplied by Git.

**These legacy scripts do not enforce the web app's dollar spending caps.** Their `--limit` controls the number of questions, not USD cost. The Ollama adapter records dollar cost as unknown. Agree on cloud access, excerpt transfer and a budget before running generation or judging. For controlled paid evaluation, use the newer [guarded evaluator](EVALUATION.md#offline-bridge-to-the-rc2-evaluator).

Work in a separate experiment checkout or make private backups of saved outputs before a deliberate rerun. Never delete the historical records just to make a command succeed. The generator opens its output exclusively **after generating answers**, so an existing filename can cause failure after model calls have already occurred. Check output names before starting.

<a id="2-optional-recreate-retrieval-predictions-from-scratch"></a>
## 1. Decide whether you need new retrieval results

The historical answer experiment used the existing predictions and only their top five document IDs per question. Reusing that file reproduces the saved input selection; it does not rerun search.

Do not use the old unscoped command as if it were the current evaluator. To run a new permission-aware BM25 experiment, follow [current retrieval instructions](EVALUATION.md#match-the-web-retriever). A new result is a separate experiment and may have different document-access rules.

<a id="3-prepare-the-20-question-evidence-batch"></a>
## 2. Prepare a new evidence file without model calls

If you only want to read the saved batch, skip this step. Otherwise choose a new file:

```sh
python -m src.evaluation.prepare_answer_batch \
  --output .cache/evaluation/legacy-bm25-cases-new.json
```

The helper reads the selected questions, saved BM25 predictions, raw UUID index and source documents. It refuses an existing output file. Optional arguments `--selected`, `--predictions`, `--benchmark`, `--expected-count` and `--top-k` make the inputs explicit. Windows long-path handling is applied only on Windows.

This preparation is a legacy development batch, not an authenticated, snapshot-bound runtime export. It does not enforce the newer frozen-split rules. Its references must never be copied into generation inputs.

<a id="4-generate-gpt-oss-answers"></a>
## 3. Generate answers only for an intentional new experiment

[The historical generator](../scripts/run_ollama_benchmark.py) reads the fixed filename `outputs/alex_evaluation/bm25_cases_20.json`. It does not automatically read the new path from Step 2. In your separate experiment checkout, deliberately install the reviewed new batch at that input path and move the old answer output to a private backup first.

```sh
python -m scripts.run_ollama_benchmark --limit 20
```

It writes `outputs/alex_evaluation/bm25_gptoss_answers_20.json`. It uses a 24,000-character evidence allowance, `gpt-oss:20b-cloud`, and temperature 0. A character allowance is not a token count; temperature 0 does not guarantee identical model output.

A single-question command is also supported:

```sh
python -m scripts.run_ollama_benchmark --question-id qst_0350
```

That creates `bm25_gptoss_retry_qst_0350.json`. It does not replace the corresponding record in the 20-question file. Likewise, `--limit 1` writes an answers file ending in `_1.json`; the judge below still expects the `_20.json` input. Do not confuse those files.

<a id="5-run-the-automated-judge"></a>
## 4. Judge the exact saved answers

[The historical judge runner](../scripts/run_ollama_evaluation.py) reads the fixed 20-answer filename and joins reference answers from `questions_20.json`:

```sh
python -m scripts.run_ollama_evaluation --limit 20
```

It writes `bm25_gptoss_evaluation_20.json`, using the [0–2 rubric](EVALUATION.md#answer-rubric). The four dimensions are correctness, completeness, citation support and abstention/limits. It records reasons and usage. It uses the same default Ollama model as generation.

<a id="6-rerun-safely-without-losing-earlier-results"></a>
### Understand resume behavior

The judge keeps successful existing scores and intentional generation-error records, skips their question IDs, and retries failed judge rows on a later invocation. It does **not** detect that you changed the model or prompt. Running it again can mix settings or incur new calls.

For a fresh experiment, preserve the original files in a private dated backup and start with a new output identity. For a retry, record exactly which rows changed. Never silently substitute a retry into an old experiment. The newer guarded runner has explicit plans, identity checks and no automatic replay of uncertain attempts.

<a id="7-human-ratings-comparison-and-reporting"></a>
## 5. Compare machine scores with human review

The scripts above do not perform human review or compute a complete reproducible human/judge agreement report. A workbook containing ratings does not change that.

1. Match the **exact answer and evidence**, not just a question ID reused in another run.
2. Have reviewers independently use the [same rubric](EVALUATION.md#answer-review-fields-and-scores), without seeing machine grades first.
3. Exclude N/A dimensions instead of converting them to zero.
4. Report exact agreement and mean absolute error. Use quadratic weighted Cohen's kappa only when the sample supports it.
5. Preserve disagreements and any later adjudicated ratings separately.

The historical scripts do not supply a human-rating or agreement-report CLI. Current critic review packets use [the calibration APIs](EVALUATION.md#critic-calibration-capture), and current answer judging uses [the RC2 bridge](EVALUATION.md#offline-bridge-to-the-rc2-evaluator).

<a id="8-tests"></a>
## Checks and remaining limits

Run `python -m pytest tests/test_answer_metrics.py -q` for the rubric parser and helper checks. Run the full suite using the [testing setup](WEB_APP.md). Passing offline tests does not verify a fresh cloud model run. Old test-count snapshots are not the current test status.

<a id="9-git-sharing-and-data-handling"></a>
<a id="10-known-reproducibility-limitations--recommended-improvements"></a>
### What to keep with a new result

Record the question-selection file, corpus revision, source commit, prediction-file fingerprint, model/version, prompt, exact selected evidence, limits, usage and output paths. Record how the curated sample was chosen. Keep historical results separate from new hybrid/Claude experiments.

Commit source, tests, instructions and approved compact result summaries. Keep credentials, `.env`, model weights, the full corpus, embeddings/indexes, private review packets and debug/retry files out of Git. Existing historical answer files contain fictional corpus excerpts; do not assume that every future evidence file is safe to publish.
